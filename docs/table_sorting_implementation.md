## Architecture findings before implementation

- The project has one shared `invoice_app/templates/invoice_app/base.html`; most pages inherit it directly or through module base templates. The only project-authored JavaScript file found is `invoice_app/static/invoice_app/button_tooltips.js`.
- No client-side table-sorting library or existing sorting helper was found in project-authored templates/scripts.
- Django paginators and row caps exist in journal, audit, document, reporting, expense, bank, attendance, backup and employee views. These are sorted on the server before pagination/capping so users sort the full filtered result set.
- A reusable client-side sorter is suitable for fully rendered body rows. It must preserve non-data summary rows, never reorder form/control grids or action-only columns, use underlying values where available, and leave empty values stable. Server-side sort parameters will be added for any capped/paged querysets after view-by-view inspection.
- No models or migrations are needed. Sort parameters, where used, will be allowlisted and use stable secondary ordering.

### Sort coverage and limits

The client enhancement is global through the shared base template, but it only enables tables with a single semantic header row, one body, and at least two ordinary data rows. Header columns that represent actions or controls are skipped. Capped and paginated tables use server-side allowlists and retain the active query filters when changing sort; pagination restarts at page one. Empty sort requests keep their prior ordering. Dashboard snapshots and short “recent” widgets keep their intentional time-based ordering.

Server-side sortable table instances: `accounting/journal_list.html`; `audit/log.html`; `document_management/list.html`; `document_generation/catalogue.html`; `financial_reporting/catalogue.html`; `reporting/_body.html`; `expense_management/all_expenses.html`, `claims.html`, `review.html`; `attendance/applications.html`, `corrections.html`; `bank_management/transactions.html`, `imports.html`, `transfers.html`; `backup/home.html`; and `employee_management/employee_detail.html`.

All other safe, fully rendered list tables are enhanced client-side when the row/header structure passes the shared safety checks. The following patterns are intentionally excluded because sorting would detach controls, alter meaningful grouping, or misrepresent a summary as a record list:

- Editable line-item/form grids, including `accounting/journal_form.html`, invoice entry line items, and tables with editable text/select controls.
- Grouped, subtotal, total, or summary rows, including ledger opening/closing balance rows and financial summary tables. Explicitly pinned opening rows remain fixed while ledger transaction rows sort.
- Preview, comparison, and nested detail layouts without one semantic header row, including backup detail key/value tables and document generation previews.
- Tables with fewer than two data rows, no semantic `<thead>`, multiple header/body sections, or only action/select columns.
- Short dashboard “recent” widgets and top-N cards where the row set is deliberately limited to recent/priority items.

The full project test suite ran 593 tests: 592 passed and one existing test failed, `invoice_app.tests.IconActionTests.test_customer_row_actions_are_accessible_icons`, because its rendered customer row lacks the expected Delete button. The failure concerns the existing customer action UI and is unrelated to table sorting; no changes were made to that action. `manage.py check`, the four new sorting tests, Playwright browser smoke checks, and JavaScript syntax validation passed.
